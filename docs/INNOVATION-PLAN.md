# Kwey Agent 原生创新与业务拓展详细规划

> 版本：v0.1 设计稿；日期：2026-11-24。
> 范围：五个候选方向的产品、架构、数据、接口、验证与商业化规划；不是实施任务卡，也不代表五项均已批准开发。
> 基线：本仓现有能力已核实；新增行为均为规划。竞品资料属于文档核查，未安装实测。文中性能、采纳率、留存与价格全部是验证目标或待验证假设，不是已有成绩。
> 决策建议：先验证 A「值班 Agent」的日常价值；B「写入溯源」是放开自动写入的前置条件；C、D 顺序扩展；E 单独通过需求与安全门禁后再投入。

## 1. 定位、边界与创新判据

### 1.1 本轮要解决的问题

Kwey 已经拥有编辑、双链、混合检索、MCP/REST/CLI、内置 Agent、知识编译、个人信息库、快照、审计、AI 收件箱、知识体检、结构化视图等能力。再次增加一个搜索入口、聊天入口或整理按钮，不构成本轮创新。

本轮押注一个更窄的问题：**用户不用每天重新发号施令，Agent 仍能持续照料知识库；同时用户能辨认、审阅、追责并撤销它的写入。** 从「Agent 能操作」变成「可以安心委托」。

现有产品规划见 [PRODUCT-PLAN.md](./PRODUCT-PLAN.md)。本文件补充下一轮候选，不改写其中已完成事项，不自动恢复已搁置任务。A 的审批队列吸收此前“Agent 写审台”的必要部分，不另建第二个竞争入口。

### 1.2 四条创新判据

1. 已存在定时任务、文件事件、会话导入等市场能力，不能声称它们是首次出现。差异必须落在本地数据主权、统一写路径、跨入口治理与低负担使用上。
2. 每项 MVP 在不重构核心的前提下，能用真实笔记库、明确输入输出与失败用例完成验证；两周指可用试点版本，不指生产级全部能力。
3. 优先复用 `VaultService`、`registry.invoke`、`preview_ops/apply_ops`、EventBus、混合检索、现有记忆与前端模式。允许补齐缺失的治理层，不复制业务写路径。
4. 产品价值以用户重复使用与实际决策收益验证；工具数量、生成字数、体检分数上涨均不能代替价值指标。

### 1.3 不在本轮范围

不重做 AI 聊天、检索、体检、捕获、收件箱整理、周期笔记、间隔复习或 Bases；不开发移动端原生 App、插件市场、通用自动化编排器、云端笔记托管、多人实时编辑；不以“支持本地文件”等同于“模型请求永不出设备”。

### 2.2 优先级：投入产出比 × 战略协同性

| 顺位 | 方向 | 投入产出比（1–5） | 战略协同性（1–5） | 乘积 | 判断 |

| 2 | B | 4 | 5 | 20 | 信任底座与产品区分度高；是 A 自动执行的硬依赖，但单独不一定带来高频价值 |

以上为主观相对排序，不是精确 ROI 或概率。A 位列第一的理由是：现有 `run_chat` 仅由聊天路由驱动（`app/api/routes_chat.py:83–107`），用户仍需主动发起；持续职责可以测试新的留存机制。市场已出现同类触发能力，所以必须以“结果好用且敢批准”获胜，而非以“能定时”获胜。

### 2.3 实施依赖与止损

```text
A0 全审批职责试点 ───→ A1 持久审批/故障闭环 ──┐
B0 actor 贯通 ─────→ B1 版本审阅与来源展示 ──┼→ A2 低风险自动执行（另行批准）
                                          ├→ C 会话蒸馏
                                          └→ D 失效语义
A/B 安全闭环 + 团队需求成立 ──────────────────→ E 独立网关试点
```

A0 可独立验证价值，但任何 A2 自动写入都必须等待 B1、版本门禁、故障恢复与预算测试通过。C/D 不必为 A0 增加实现负担。E 不因代码复用度高而自动进入排期。

## 4. A：值班 Agent 详细规格

### 4.1 用户任务与价值承诺

典型用户每天捕获碎片、使用不同 Agent、偶尔整理知识库；困难不是没有按钮，而是“忘了做”“每次都要重新说”“怕自动改坏”。

价值承诺：用户启用一个职责，设定范围与时间；Kwey 在应用运行期间检查；有实际改动才形成带证据的提案；用户在一个队列批准；过时提案不会覆盖新编辑。首版不承诺设备休眠期间执行，也不承诺全自动维护。

### 4.2 MVP 与非目标

MVP 限三个内置职责：收件箱值班、每日知识简报、每周健康巡检。每个职责可独立启停、手动试跑、调整时间/目录/上限，均默认关闭。只提供固定 schema 配置，不允许脚本、shell、任意 URL、任意插件或任意模型工具。

首版所有笔记写入都须审批。允许用户勾选独立提案，但不能任意截断有顺序依赖的同一 ops 组。不做无人值守删除、覆盖正文、重命名、回滚、清空回收站；移动仅可进已有允许目录。A2 自动层另行评审。

### 4.3 用户流程

1. 打开“值班”面板，启用一个职责。显示将读取的范围、可能产生的改动、模型端点、运行预算与“应用关闭不会运行”。
2. 首次试跑只读，展示“查了哪些笔记、为何建议、预计改哪些文件”。未配置生成模型时仍可规则扫描；不得伪称 AI 已运行。
3. 提案进入审批队列，展示来源、before/after、目标路径、关联链接影响、模型/职责名称、基准版本。没有实质差异则记 `no_change`，不通知。
4. 用户批准指定提案版本。服务端重新校验权限、配置、预算、来源与目标版本；不接受浏览器传来的“新 after 文本”替换已审提案。
5. 成功后可打开结果和审计；失败显示已完成/未完成/不确定项，不能把部分失败显示为成功。拒绝和静音不修改笔记。

### 4.4 三个职责的可执行规格

| 职责 | 输入与默认触发 | 候选与建议 | 写动作及约束 | 去重与无模型行为 |
|---|---|---|---|---|
| 收件箱值班 | 启用后每日一次；可选对 inbox 新增/更新静默等待30秒；每轮最多10条 | 复用收件箱建议算法，范围必须在配置的 inbox；已有目录/标签白名单 | MVP 仅补标签、移动；不改标题/不覆盖正文；同一笔记动作组成有序组 | 候选内容哈希+职责版本去重；原样保留不生成“整理”提案；无模型只报告积压 |
| 每日知识简报 | 本地时间18:00；最近一天、最多20篇，排除输出目录 | 复用周期候选选择规则和 pulse 的事实统计；提取变化、关联与明确待办，每项带实际来源 | 预览后创建 `daily/YYYY-MM-DD-知识简报.md`；已有文件则冲突，不自动覆盖或追加 | 日期+输入哈希去重；无模型可生成事实清单，明确“规则版”，用户仍须批准 |
| 每周健康巡检 | 周日18:00；指定目录，先 `scan(deep=False)` | 复用六类体检；只列最重要的≤5项及证据，不再创造体检引擎 | 巡检结果保存在职责控制记录中；若用户选“保存报告”，创建普通 Markdown 提案；不自动修复/删除 | 相同问题集合哈希不重复提醒；无模型完全可用；深度重复检查只允许手动 |

职责范围不是给 prompt 的建议，而是宿主读取/生成/执行的硬约束。每日简报的“待办”只能源自实际勾选项或明确语句；模型推断必须单独标为建议。

现有收件箱/周期代码依赖全局 `deps`；应抽出接收 `vault/db/config` 的内部只读服务函数，再由路由和职责共用。不得让 worker 通过本机 HTTP 调用可能落盘的 GET 或 `apply` 端点。

### 4.5 架构与安全执行面

```text
Timer / EventBus（只做轻量过滤与入队）
  → DutyRuntime（固定 vault 实例、generation、有限队列）
  → 单 worker（只读候选收集 → 固定职责适配器 → 可选 LLM）
  → 结构化 ops 白名单校验 → preview_ops + 影响文件 manifest
  → 持久 ProposalStore → 队列 UI → approve/reject
  → 锁内版本预检 → 逐项 apply_ops/VaultService → 状态、溯源、审计
```

建议新增 `app/duty/{runtime,store,recipes,policy}.py` 与 `app/api/routes_duty.py`。控制状态存 `.kwey/duty.db`（单独 SQLite，含 schema_version），不混入可删除重建的 `index.db`。笔记事实仍在 Markdown；审批、run 和故障状态是控制数据，不能靠重建索引恢复。

复用内核的两条规则：

- MVP 先用固定职责适配器和 `chat_json` 产生 ops，减少通用循环的不确定性。不要简单把 `run_chat` 塞进 Timer：当前循环会立即执行普通写工具。
- 若职责确需多步检索，`run_chat` 增加仅内部可传的 `actor` 与 `allowed_tools/read_only` 执行策略；先过滤暴露工具，再在 `registry.invoke` 前二次拒绝所有非白名单/有副作用调用。规划模式不支持 resume，不可被模型的 `confirm=true` 绕过。默认聊天行为保持兼容。

A/B MVP 不新增 MCP 工具，contract 工具数仍为28。新增职责 API 是内部产品接口，不伪装成已有 contract 能力。

### 4.6 生命周期、去重与限额

- EventBus 回调在发布线程同步执行（`events.py:78–88`），只允许规范化路径、排除目录与入队；严禁在回调内跑模型、读全库或持有长锁。
- 每个打开的 vault 一个 runtime；一个 worker、一个 Timer/职责。待运行队列上限20；同职责同输入合并。单轮最多10个 ops、单提案20个受影响文件、单文件正文读取≤50k字符；超过只报告需人工处理。
- 同一职责同一输入哈希、配置版本和日期桶构成幂等键。拒绝后相同输入不再次提醒；输入变化可以形成新版本。保留拒绝原因，但不自动上调写权限。
- 每职责最多2轮/小时，默认最多3次生成模型调用/轮、总字符输入≤24k；这是预算限额，不是 token 计费等价。统计有无 provider usage 分开，缺失时价格记 unknown。
- 首版无需全天后台常驻服务。启动补跑仅合并最近24小时内最后一个未完成定时槽；错过一周不补七份。文件事件不持久，因此启动时重新扫描职责范围。
- 切库前停止接新任务、取消 Timer、解绑旧 bus、增加 generation；运行中的网络请求可以到超时才返回，但结果必须因旧 generation 丢弃，绝不写向新库。worker 捕获明确 vault 实例，不在中途读取全局 deps。
- `server.py:42–61`、`routes_system.py:36–49` 是启动/退出/切库接线点；照 `ws.py:48–54` 的解绑再绑定模式。测试必须覆盖旧 bus 不再触发和旧任务结果丢弃。
- 职责输出不再次触发自身：排除简报目录、忽略当前 run 的写事件、冷却与输入哈希共同防回环；不能只依赖 watcher 自写去重，因为 service 自己也会 publish。

### 4.7 持久数据模型与状态机

| 对象 | 最小字段 | 约束 |
|---|---|---|
| DutyDefinition | id、recipe、enabled、scope、schedule、limits、config_version、（读出附 scope_required） | recipe 枚举；scope 为合法相对目录；MVP 策略只能 manual；scope 为空时仅 scope_required=true 的职责不可运行 |
| DutyRun | run_id、duty_id、vault_generation、input_hash、slot、status、started/ended、model_usage、error_code | 幂等键唯一；失败/限额/未配置模型独立状态 |
| Proposal | proposal_id、run_id、version、ops、diffs、manifest、sources、reason、proposal_hash、status、expires_at | 审核对象版本固定；正文敏感信息不进普通日志；默认7天过期 |
| ManifestEntry | path、exists、raw_sha256、mtime、role（输入/写目标/链接影响） | 哈希为正确性门禁，mtime 为快速检查；创建目标也记录“不存在” |
| ApplyItemState | proposal_id、op_index、intent_at、result_at、status、result_paths、error | 执行前后记状态；支持 applied/failed/uncertain，不把 intent 当成功 |
| Decision | proposal_id、version、decision、actor、ts、reason | approve/reject 原子抢占；重复批准返回既有状态，不再次执行 |

Run：`queued → running → no_change / awaiting_review / failed / budget_exceeded / skipped`。

Proposal：`pending → rejected / expired / stale / applying → applied / partial / uncertain`。`applying` 在进程退出后不能自动恢复成 pending；先标 interrupted/uncertain，人工对照实际文件。

### 4.8 审批正确性、链接与故障恢复

复用 `preview_ops` 的 diff，但增加源文件/目标不存在状态/移动导致的反链受影响文件清单。现有 move 预览不等于展示所有后果；应在预览阶段复用 LinkGraph/LinkRewriter 的解析规则确定影响，不用另一套正则猜测。

批准时在同一 `VaultService.lock` 中预检全部 manifest，确保没有新的进程内写插入；每项执行前再检查对应文件与目录状态。批量总量有上限，避免长时间阻塞编辑。外部编辑器不遵守这把锁，哈希预检仍存在检查与落盘间竞争窗口；首版不能宣称任意外部并发下原子事务或零覆盖。

同组存在依赖动作时，预览必须使用影子文档集按顺序推演，不可把现有逐项独立preview当作多步语义保证。为每一步保存expected_payload_after、expected_path_after与预计链接变更；执行后校验实际结果并保存其raw hash作为下一步基线。tag→move不能拿最初的raw hash检查已被本组合法修改的文件；服务生成的updated/溯源字段变化也不能被误判为外部冲突。

首项落盘前发现任何版本变化，整组标stale、停止应用并要求重新预览；已有副作用后再出现冲突则记partial，无法判断落盘结果则记uncertain，保留逐项记录。均不静默rebase。依赖动作必须一起审核，如tag后move；“选择部分”仅选择独立提案。

`apply_ops` 是逐条执行、无全批回滚（`ops.py:209–266`）。故障记录逐项已执行结果；普通删除不在 MVP 白名单。快照未启用时明确“无历史回滚”，不能用默认不存在的快照作安全承诺。

SQLite 事务不能与文件 rename/write 组成分布式事务。若文件已落盘但结果未记账，重启显示 uncertain，禁止自动重跑 append；先读实际内容/路径、比对预览并让用户选择确认完成或重新提案。首版保证重复批准不会重复执行；不声称断电边界的 exactly-once。

默认待审7天过期；终态提案的before/after与来源摘录再保留7天后由专用服务清除，run/decision的无正文概要保留90天。partial/uncertain未解决时不自动清理必要恢复材料，先提醒用户处理；用户可明确放弃并清除。每vault最多100个未解决提案、正文控制数据100MB，触顶停止产生新提案，不静默删待审内容。保留期与导出范围在UI可见，不能把“过期”误写成“已安全擦除磁盘备份”。

### 4.9 API 草案（新增，尚未实现）

所有接口沿用 `{code,data,message}`；新接口使用 `require_token`。模型不能批准自己的提案。

| 方法与路径 | 权限 | 输入/输出关键字段 | 行为 |
|---|---|---|---|
| GET `/api/duty` | read | definitions、runtime_state、pending_count | 不触发运行 |
| PUT `/api/duty/{id}` | write | enabled/scope/schedule/limits/config_version | 校验固定职责与版本；不能设置 auto |
| POST `/api/duty/{id}/run` | write | config_version；返回 run_id/status | 异步入队，不等待模型，不写笔记 |
| GET `/api/duty/runs` | read | limit/cursor；返回脱敏概要 | 详情需明确请求，不展示密钥/完整 prompt |
| GET `/api/duty/proposals` | read | status/cursor；返回摘要 | pending/stale/partial 可分别查看 |
| GET `/api/duty/proposals/{id}` | read | version/diffs/sources/manifest摘要 | 正文读取受同等 vault 权限保护 |
| POST `/api/duty/proposals/{id}/decision` | write + 本地人工审批边界 | version/proposal_hash/approve或reject/reason；approve另需approval_grant | approved 仅此版本；401/403/409/410分开 |
| POST `/api/duty/pause` | write | all或duty_id | 立即禁止后续调度/应用；网络调用可到超时返回 |

read/write/admin 不能区分“外部 Agent 的 write”和“本人批准”：这不是现成权限能力。MVP decision 必须额外接受桌面主进程授予的一次性审批凭据，不对普通Agent token开放批准能力。建议流程：用户在UI选择提案 → 桌面主进程显示包含路径/动作/版本的原生确认 → 确认后生成随机grant，绑定proposal_id/version/proposal_hash/vault_generation，60秒有效且仅可消费一次 → decision同时校验token、grant和版本。HTTP端点不能凭write token自行申请grant；拒绝决定只改变队列状态，仍须校验本地会话与CSRF。

新增桌面审批桥是计划中的代码，不是已存在API；需要把`main.py`及专用桥模块纳入唯一写者范围，并验证原生确认组件的实际接口。纯浏览器`--server`模式首版仅报告/预览，批准apply默认关闭；不能用localhost、Origin或User-Agent单独充当人的身份。此设计隔离普通工具权限，但不能抵抗能操控本机桌面/主进程的恶意程序，不声称密码学意义上的“真人证明”。

状态通知优先轮询，降低改动量。若新增 EventType 用于 WS，仅传 run/proposal id 和状态，不传 diff 正文；同步更新 VaultEvent 数据结构、SSE 与前端消费者，不能臆定旧事件支持任意 payload。

### 4.10 前端信息结构

复用 inbox overlay 模式，新建 `static/js/duty.js`，从 ribbon/命令面板进入。三个页签：职责、待审、运行记录；pending 徽标只在有实质提案时出现。紧急暂停始终可见。

提案详情新建共用 diff 呈现函数，使用 textContent/安全 Markdown，展示插入/删除、来源链接、移动前后路径、受影响链接数、版本变化提示。无现成共享组件可直接拿来；不要通过 raw innerHTML 展示模型文本。支持键盘导航、焦点恢复、空态、加载/断网/冲突/部分成功、窄窗口及 reduced-motion。

## 5. B：写入溯源与信任分级详细规格

### 5.1 产品目标与诚实边界

用户能回答：“这篇是谁最后改的？是不是 Agent 写的？我看过的是不是当前版本？这一批来自哪个职责或会话？”默认筛出 AI 未审内容，避免未经确认的片段被当成本人的最终立场。

B 是**本机协作溯源和版本审阅**，不是文本 AI 检测器、作者鉴定或防篡改证据链。任意程序能直接改 Markdown/frontmatter；本地文件、Token 名称、MCP 进程名称都不提供不可抵赖身份。品牌表述应是“记录经 Kwey 写入的来源，并提示外部变化”，不能声称任何绕过都可完美追踪。

### 5.2 字段与状态

采用 `kwey_` 命名空间，避免占用用户原有 `source/title/reviewed_at`。保留业务来源字段，不把剪藏 source 覆写成 actor。

| 字段 | 值/用途 | 写入规则 |
|---|---|---|
| `kwey_writer_kind` | human / agent / system / unknown | 宿主决定；不信任模型传来的同名字段 |
| `kwey_last_writer` | local-ui、kwey-built-in、mcp-stdio、token名称、duty:inbox等 | 经服务端 actor 上下文生成；名称用于显示，不是身份密码 |
| `kwey_run_id` | 可选职责/会话批次 | 内部传递；未提供则为空，不制造假关联 |
| `kwey_generated` | 当前语义版本含 Agent 派生内容的保守标记 | Agent正文/业务字段写入置true；人工小修改不自动清false |
| `kwey_reviewed_at` | 明确人工审阅时间（ISO带时区） | 单独审阅动作设置，普通保存不等于审阅 |
| `kwey_reviewed_hash` | 人工确认时的 payload SHA-256 | 与当前payload一致才显示“当前已审” |

payload hash = 正文 + title/tags等用户业务 frontmatter 的稳定序列化；排除 created/updated 与 `kwey_` 管理字段。仅管理字段更新不引起无限审阅失效；正文/标签/标题变化均须重新审阅。序列化规则版本必须固定并测试 YAML 日期、Unicode、顺序与换行，版本变化不得让旧 hash 被误当有效。

派生状态：`unknown`（无可靠基线）、`agent_unreviewed`、`agent_reviewed_current`、`human_or_system_current`、`external_changed`。writer_kind、generated、reviewed 是三个维度；不能把“最后是人保存”自动等同于“整篇已验证”。批准 A 提案也不自动宣称事实正确；可提供单独“同时审阅此版本”复选框，且只能在用户看到了完整实际结果时启用。

### 5.3 Actor 贯通方案

新增 `app/vault/provenance.py` 定义 ActorContext 和规范化/hash/审阅规则。Actor 含 kind/name/origin/run_id；权限role与writer_kind分开，admin不等于human。

- `create_note/write_note/write_raw` 增加 keyword-only actor，现有位置参数调用保持兼容。优先显式 actor，其次内部 ContextVar，均缺失则 unknown；不能默认 human。
- `registry.invoke` 在调用 handler 期间设置 ContextVar，用 try/finally 恢复；REST 从 TokenStore 校验记录产生 agent actor，MCP 从启动配置产生 agent actor，内置聊天从内部固定身份产生 actor，不接受客户端自填 kind=human。
- `kernel.run_chat` 可接内部 actor；职责把 run_id 带入实际执行。ContextVar 不自动跨线程，worker 显式传 actor；拒绝共享一个可变全局 actor。
- `apply_ops` 增加 keyword-only actor，用于职责/F1等内部调用。非registry写路径如收件箱、体检、剪藏、编译、模板、复习、导入和Bases逐项登记身份；AI生成后人点击“应用”仍保留 agent派生身份与人工批准者，不能洗成纯human。
- 普通UI编辑路由显式标记 local-ui；这是本机应用约定，不是抵抗本机恶意调用的认证。E 必须用独立已认证网关，不延用这一假设。
- CLI普通write目前不走registry actor；可由CLI内部标记 unknown/cli，后续允许操作描述名称，但用户自报名称不得标为 verified身份。

### 5.4 语义修改、链接重写与外部修改

`write_raw` 用于链接重写（`app/vault/links.py:62`），当前不会刷新frontmatter updated（`service.py:282–297`）。因此不能用“磁盘mtime比updated新”判断外部编辑；那会误报正常移动反链。

实施规则：服务写后记录最后已知 raw/payload hash；普通写与write_raw统一更新溯源基线。链接重写应记录system来源及发起run，保留原generated状态，因payload改变使旧review hash自然失效；允许只更新管理字段，不改变无关用户字段。移动主文件只有路径改变时不伪造正文作者，路径变更留操作记录；引用它的源文件才发生内容版本变化。

watcher先按现有自写去重流程处理，再对有已知基线且hash变化的外部事件标记external_changed；**只更新索引/溯源状态，不自动重写外部文件**。未知旧文件仍为unknown。重启时按基线核对变化；没有基线、哈希相同或监控漏事件不能凭空推出外部作者。

基线与事件由专用ProvenanceStore保存在 `.kwey/`，原子保存、有限保留；可重建当前hash但不能重建历史身份。现有500条journal复用为概要展示，不作为完整溯源源。删除基线后全部降级unknown，而非human。frontmatter中的身份与hash为可携带声明；本机基线丢失/导入他人库时标“声明未校验”。

### 5.5 审阅、筛选与检索规则

编辑工具栏显示“Agent改写·未审”“已审当前版本”“来源未知/外部改动”，点击展示来源和最近run；属性面板可看到字段，但管理字段只读。审阅弹窗显示当前版本，并提交path+expected_payload_hash；服务端重新读取，不符409。审阅仅写管理字段，走VaultService，不直接写Markdown。

Bases可用已有frontmatter列展示writer/generated；“当前已审/外部变化”是运行时计算状态，需要在snapshot/schema中增补只读派生字段，不能假设现有schema已支持公式比较哈希。

MVP新增 `/api/provenance/note?path=...`（read）和 `/api/provenance/review`（人工边界+write）；复用A的人工审批通道，避免两个身份机制。首版不新增`writer:`搜索操作符；若后续增加，必须同步parse_query、hybrid过滤、FTS路径与contract文档。

B首版在RAG来源旁提示未审/未知，不默认全量降权或排除；审阅不是事实正确性的保证。D再引入明确失效语义。用户要严格只用已审证据时必须明确选择；数据不足返回不足，不静默放宽。

### 5.6 迁移与隐私

旧库零批量改写：按需显示unknown，新写入才补字段。管理字段冲突先提示，不自动覆盖用户已有同名字段；确定迁移前按proposal-first出预览。快照回滚后的字段可能回到旧版本，必须重新核对实际hash，不能保留错误“已审当前”。

默认溯源日志只记录actor/run/path/hash/时间/动作，不保存全部正文与provider prompt。需要diff恢复时受A的提案保留策略保护。明确 `.kwey/` 可含敏感路径、审批正文、密钥配置，不能未经确认加入git或审计导出。溯源不是加密，不能宣传磁盘被盗仍安全。

## 6. C：跨 Agent 会话蒸馏与交接

### 6.1 差异化与边界

会话导入、导出与摘要已有市场供给。C 不以“支持聊天导入”作为创新主张，而是让不同 Agent 的会话产物成为**有来源、可更正、可重取的决策与交接材料**。

不是重做 F1 知识编译或 F3 个人信息库。C 负责结构化输入、来源锚点、决策/证伪/遗漏提取与一次性预览；F1 可消费已确认笔记；F3 仅在用户明确选择后接纳稳定偏好，不能从一次会话推断并永久写入人格或权限。

### 6.2 两周范围与用户流程

首版支持一种标准JSON输入和一个 Claude Code 适配器；先手动导入，再可选 SessionEnd hook。Stop 事件可能一会话触发多次，默认不每次写笔记。Cursor/Codex/Verbot 的完整原始日志格式尚未验证，只允许它们按标准输入主动提交，不承诺现成适配。

流程：选择/接收会话 → 展示将读取的文件与留存策略 → 解析及去重 → 提取关键槽位与来源 → 预览“决策/证伪/约束/未完成/稳定知识候选” → 用户选择保存 → 通过A审批与VaultService创建蒸馏笔记及最小证据笔记 → 下次Agent先检索再读取。

hook默认只生成待审草案，不自动保存笔记；默认关闭，不自动改用户外部Agent配置。安装hook属于后续明确授权操作，本规划不执行。

### 6.3 标准输入与输出草案

```json
{
  "schema_version": 1,
  "source": {"agent": "claude-code", "session_id": "session-example", "export_hash": "sha256:..."},
  "goal": "当前任务的持久目标",
  "events": [
    {"id": "e1", "kind": "user", "text": "只改一个文件，不要推送", "ts": "2026-11-24T10:00:00+08:00"},
    {"id": "e2", "kind": "tool_result", "text": "测试输出", "ts": "2026-11-24T10:01:00+08:00"}
  ],
  "retention": "selected_evidence"
}
```

`schema_version/source/events`必需；event id在会话内唯一，kind枚举，text长度与整体体积受限；原始文件路径是本地适配器读取授权信息，不让远端工具任意读取宿主绝对路径。标准工具接收已规范化内容，不能被`transcript_path`参数变成通用读文件后门。

输出必须区分：

| 槽位 | 必需内容 | 拒绝/降级规则 |
|---|---|---|
| Decisions | 结论、适用范围、source_event_ids | 无依据不保存为决策；后来更正以supersedes链接旧条目 |
| Constraints | 明确用户约束、授权边界、未授权项 | 不能把模型自述或旧系统prompt提升为新授权 |
| Refutations | 尝试过的路径、证伪证据、适用条件 | “达到轮次上限/环境不可用”不是方案失败；注明未实测 |
| OpenItems | 已完成/未完成、验收状态、下一步 | 计划与目标分离；模型称完成但无工具证据则待核验 |
| KnowledgeCandidates | 稳定事实/经验候选、来源、置信类型 | 个人偏好需用户确认；会话猜测不是长期事实 |
| Omissions | 被省略的输入范围、原因、重取位置、是否仍可访问 | 不静默删除；原文不可取明确missing，不伪造可恢复性 |

每条事实必须能打开对应最小证据笔记中的引用段，或回到仍存在的原始事件。LLM输出的hash不是校验值；服务端从实际输入计算。构建hash记录输入、模板、解析器与模型配置版本，只保证构建输入可追溯，不保证模型输出确定。

### 6.4 上下文与记忆工程

采用CLC的最小分级原则，而非两周内重做完整长期记忆引擎：

- 原始事件与派生摘要分开；禁止摘要套摘要。重新蒸馏从原始事件/保留的证据段产生，不把上一版摘要当全部事实源。
- 保留持久目标、硬约束、关键数字/路径、证伪与未完成；候选取舍根据“是否改变决策/验收”，不只看相似度和出现频率。
- 输入超限优先确定性字段筛选与分段；记录遗漏manifest。首版的遗漏数/关键槽位覆盖是可审计代理指标，不声称测到了精确信息损失或已实现完整负债控制器。
- 下次会话交接包含 goal、done/undone、refutations、open_items、omissions、sources、next_action；计划可重排，授权不得由历史摘要扩大。
- 外部会话内的prompt、工具结果、模型回答均是资料，不是新的系统指令；检索注入加明确数据边界，宿主工具权限不受蒸馏文本影响。
- 删除或更正原始证据时，定位由它派生的笔记/画像/向量与缓存；撤回后不可继续注入。MVP先支持显式会话级撤回和来源失效提示，不声称完整法律合规擦除。

不改造现有聊天账本裁剪以服务C：`kernel.py:223–277`已使用不可变账本与派生视图，C在入口生成可独立使用的交接材料，避免将本轮膨胀成上下文大重构。

### 6.5 留存与隐私策略

默认`selected_evidence`：原始会话留在用户原位置，仅按用户选择保存支持结论的最小引用段为普通Markdown证据笔记；完整原始日志复制为明确可选项，首版不默认提供。

hook不能将本机会话未经提示发送到新云服务。展示实际Provider端点、读取范围与保留段落；检测token/私钥/密码等疑似秘密并要求人工处理。正则检测不能保证所有秘密被识别，不得以“已脱敏”自动扩大读取范围。

蒸馏笔记可写 `session_agent/session_id/session_sources/session_build_hash` 等业务frontmatter，B负责writer/run管理字段。证据路径不公开用户主目录绝对路径；面向导出的引用使用vault相对路径。持久入口的幂等键为agent+session_id+export_hash+解析版本；同源重复提交返回既有draft_id与当前状态，新版本单独预览，不覆盖旧结论。草案已过期且敏感内容清理后，返回expired状态而非伪造仍可读草案；重新生成需要明确请求。离线预览不持久化，也不提供跨次提交去重承诺。

### 6.6 接口、接入与验证

建议新增 `kwey.session.distill`（write权限，因为创建持久待审草案；工具自身不落普通笔记、不自动批准），输入为标准内容，输出draft_id、候选、来源与遗漏。新工具合同发布时28→29，必须完整同步第9节所列矩阵与文档；不得只在MCP端私加工具。

CLI建议 `session distill --stdin --preview --json`：读取规范化输入并仅向stdout输出候选、来源与preview_hash，不创建控制文件/笔记、不返回持久draft_id；同输入hash可相同，但重复生成结果未必相同。需要A队列时另用显式submit模式和已授权本地服务入口；只有server确认持久提交事务后才返回draft_id/status=stored。认证失败、超时或连接中断不能打印“已入队”；不确定提交结果以幂等键查询实际状态后再重试。

纯CLI离线模式不悄悄启动server，也不能宣称草案已入GUI队列。CLI预览与MCP持久草案的行为差异须写入合同。hook示例读取官方输入的`transcript_path`后交由独立适配器解析，不能猜测原始JSONL event字段。

实施顺序：D1–D3 标准schema/来源/hash/幂等；D4–D6 解析器和候选提取；D7–D8 A/B接线、来源笔记预览；D9–D10 一个真实hook样本与回归。未获得真实日志样本时只交标准输入版本，明确原始适配未实测。

验收集至少20段会话，含数字/路径/授权边界、纠错、未完成、工具失败、恶意提示、超限、缺原文与重复输入；由人工标注关键槽位作为基准。核心槽位覆盖率≥90%，硬约束槽位100%，无证据新增事实0；这些是目标，正则重合不能代替人工正确性。

## 7. D：知识保鲜与失效语义

### 7.1 产品问题与范围

现有体检stale只表示mtime超过阈值（`diagnose.py:146–149`）；间隔复习表示记忆练习计划，不表示知识已失效。D补的是“事实有效范围与替代关系”，不另建陈旧扫描和提醒中心。

首版针对用户明确声明：项目规则、工具配置、价格/政策、阶段性决定；不让模型自动判定所有笔记真伪，不自动浏览外部网站验证，不把旧日期的历史记录判错。

### 7.2 字段与状态规则

| 字段 | 语义 | MVP约束 |
|---|---|---|
| `valid_from` | 当前事实起始时间 | 可选ISO时间/日期；缺失不补猜测值 |
| `valid_until` | 明确到期点 | 规范化为带时区时间；日期定义为该本地日结束后的排他边界 |
| `superseded_by` | 替代笔记的完整相对路径 | 不用模糊basename；存在性、环、保留目录校验 |
| `fact_scope` | 事实适用领域/项目/实体的用户标签 | 候选缩窄，不作为模型推断事实正确的证据 |
| `verified_at` | 人工/明确验证流程验证时间 | 与B的reviewed分开：看过不等于验证过；注明验证方式 |

状态：current_declared、not_yet_effective_declared、expired_declared、superseded_declared、unknown、invalid_metadata。有效区间统一为[valid_from, valid_until)，缺失端点按无界处理；全部生命周期字段缺失则unknown。只有一个有效时间边界仍可按该边界判定声明状态，但current_declared不等于事实已经验证。当前/as_of早于valid_from则尚未生效，不能作为该时点的现行规则；到达valid_until则过期。起点晚于终点、日期非法或替代目标缺失要提示invalid_metadata，不悄悄降成正常。

单跳替代在MVP足够；检测自指/环，不无限追链。替代关系不自动规定过去何时失效：历史模式结合原笔记区间与替代笔记的valid_from评估，替代生效时间缺失时只提示关系，不按今天的替代状态降权历史证据。不能自动把原笔记删除、隐藏或改写成新观点；原始历史保留。严格只用当前知识模式遇unknown要提示不足，非严格模式显示证据状态。

### 7.3 读取、检索与写入共同门禁

- 笔记工具栏/来源列表展示明确失效与替代路径；可打开原始记录。与A待审共享队列，不再建独立“保鲜待办”。
- 默认当前事实查询中，在候选融合之后、最终截断之前对尚未生效/expired/superseded降权，并优先补入在该时点有效的替代证据；FTS、vector、hybrid与RAG口径一致。不能只修RAG而让Agent搜索继续无提示。
- 用户明确查询历史期间时按as_of评估有效范围，不按今天强行压低；自然语言识别仅作提示，首版提供明确“当前/历史日期”参数，避免误判。
- `kwey.search`与`kwey.read`返回可选freshness元数据；旧调用方忽略新增字段不受影响。参数与返回形状变更同步contract/schema/矩阵，不能预先假定已有as_of。
- 在A提案预览和批准重检中识别相关有效期/替代目标。失效来源不能悄悄被用来更新“当前规则”；生成冲突提示，需人审。模型只建议可能冲突，不有权自动撤销旧事实。
- 根据fact_scope/path/tag缩窄，最多取5份相关证据比较。不得每次写一个字都全库做LLM矛盾检测；检测无配置/超时返回“未检查”，不能冒充“无冲突”。

新增 `app/freshness.py` 纯规则；利用现有props与视图查询做候选，状态不需要另建知识图谱。批准提案后改有效期仍须通过VaultService并使语义审阅hash失效。

### 7.4 用户工作流与两周验证

先人工为50篇真实笔记标注20篇明确过期/被替代、20篇当前、10篇无声明；选同一主题的冲突版本。D1–D3字段规则/时区/环与来源展示；D4–D6检索/RAG一致过滤及历史模式；D7–D8提案门禁；D9–D10盲测与回归。

用20个问题比较同一库/同一模型的D关闭与开启：记录答案用的来源、是否误用过期内容、当前证据召回与“资料不足”。目标过期误用率相对降低≥50%，当前证据召回下降≤5个百分点；另用10个历史问题确认没有按今天抹掉过去正确事实。基线误用率为0时相对降幅无定义，应报告绝对值而非造提升。

生产推进条件：日期规则和替代路径负例全通过，检索/RAG/Agent读的状态一致；人工发现误伤可一键关闭降权。AI自动提有效期、外部实时事实核验、全库矛盾图均后置。

## 8. E：小队自托管版与商业模式

### 8.1 客群与收费对象

候选客户是3–10人的咨询、研究、独立开发、合规敏感小队，已有自托管/私有git能力，愿意为Agent接入、责任分配、权限治理与省心部署付费。不是追求多人同时编辑的Notion替代客户。

收费对象是**团队治理与交付能力**，不是用户的数据所有权、基础笔记读写或云端同步。个人版本地编辑、检索、导入、导出和既有Agent接口不因E上线降级。

以下为待验证报价，不是市场已接受价格：$3–10/席位/月等价区间，用于报价敏感性访谈；同时比较按年离线许可+部署支持、买断主版本+付费升级。离线许可证本地校验、不要求内容上传；生产版不采用频繁联网席位心跳。实际税费、地域币种、续费与席位浮动另行定价。

### 8.2 两周先验证什么

E第一阶段不是网络代码冲刺：访谈5–8名有真实团队预算的负责人，展示A/B审批和责任追踪原型，明确部署主机、知识范围、写者人数、谁批准、是否接受无实时协作与Provider边界。

判定需求成立：≥3家有明确库/负责人/时间的试点承诺，≥2家认可明确报价与采购路径；“听起来不错”不计。未成立停止团队开发，保留个人路线。价格口头认可不是已付费收入，需后续订单验证。

若需求成立，下一独立两周只做一台用户管理的主机、3–5身份、一个指定vault、单写者队列，验证有界部署；TLS、所有权限负例与备份恢复未过，不进行公网发布。

### 8.3 架构：不能直接开放桌面服务

当前`main.py:141,177`绑定127.0.0.1；普通`/api/note`、settings、vault/open路由无统一token，WS对本地无token有兼容放行（`ws.py:116–134`）。这些是桌面边界，不是可直接公网暴露的团队服务。

推荐新增独立gateway应用，默认拒绝：

```text
成员/Agent → 用户管理的TLS反代 → Gateway（认证、ACL、配额、审批角色）
                                      → 单vault服务 / registry.invoke
                                      → Markdown + 索引 + 控制账本
桌面普通UI路由不被gateway挂载；不转发任意/api/*或/file/*。
```

gateway只开放已审核的工具/审批/只读事件路由，不提供打开任意vault、宿主任意文件、Provider密钥管理、安装插件或桌面设置接口。路径scope/笔记权限在工具执行前和引用/事件输出处统一检查；不能仅隐藏UI按钮。

TokenStore的read/write/admin是角色基础，不具备团队成员生命周期、审批职责与目录ACL（`auth.py:129–207`）；新增成员/服务身份与scope授权配置。只读角色不能写，writer不能批准自己的提案，reviewer只能批准可见范围内的当前版本；团队管理员不默认变成宿主系统管理员。

E以独立gateway的人类成员审批通道替代A的本机原生桥：human_member与service_agent必须分别签发凭据，审批角色仅可授予human_member，Agent服务身份即使有write/admin也不得批准任何提案，不仅禁止自批。人工会话认证、短时重新确认/防CSRF与绑定提案版本的单次grant均由gateway执行；Agent令牌不能换取人工grant。成员审批仍不能证明账户未被恶意控制，须保留撤销、审计与风险提示。该替代机制属于E新安全能力，不通过改监听地址复用桌面审批假设。

MCP现有`KweyMCPServer`只处理stdio消息（`mcp_server.py:72–175`），其JSON-RPC分发可以复用，网络传输不是“改一个端口”。首版优先现有REST contract；HTTP MCP可作为后续独立适配，协议版本/初始化/session/SSE/取消行为需按届时官方规范验证，不猜测现有2024-11-05 stdio实现已支持。

### 8.4 数据与一致性承诺

团队版是“文件所有权与部署控制在用户手中”的local-first延伸，不是每位成员设备都有离线可编辑全量副本。首版知识库事实源在用户指定主机的Markdown；远端成员通过自有gateway访问。若要求每端离线编辑和自动合并，不进入此MVP。

单个vault写队列串行；带hash/mtime版本检查；不支持同时编辑同一篇的自动合并。git远端由用户管理，autopush保留其本来能力，不冒充多写者同步协议。临时断网不丢失已确认服务端写入；客户端未收到结果时查询run/proposal状态，不直接重放写请求。

备份包含Markdown与必要治理账本、成员/权限配置；密钥单独加密/权限保护。恢复演练须核对索引可重建、审批不能重复、已审hash正确；不能只演示复制文件。团队审计支持脱敏导出和保留期，正文默认不导出；需求若涉及不可抵赖/法定保留，需额外安全与法律评估。

### 8.5 本地优先/隐私品牌冲突评估

| 冲突点 | 风险 | 产品约束 |
|---|---|---|
| 团队共享使数据离开个人设备 | 把“本地”宣传成绝不传输会误导 | 明确传到用户自有主机与授权成员；不传Kwey运营方内容服务器 |
| 使用云模型 | 自托管gateway不等于推理离线 | 默认展示真实端点，提供本地模型/规则模式；启用云模型需单独确认读取范围 |
| 席位收费和账号 | 破坏零账号/可离线叙事 | 个人版零账号；团队身份由团队管理；离线许可，不设Kwey账号作为读文件前提 |
| 自动遥测/审计上传 | 治理成为新的隐私泄漏 | 默认无内容遥测，审计本地；支持包与诊断导出先预览脱敏 |
| lock-in与停付 | 无法迁出削弱文件所有权 | 停付不锁Markdown/导出/个人版；付费治理策略与维护服务可停止升级但不扣留数据 |

结论：**有条件兼容，但不是零冲突。** 自托管、离线许可、个人版不变、无内容遥测只能缓解；需要在命名、安装流程与营销文案中明确“用户自有团队服务器”与“个人完全离线”的区别。任何默认官方云托管/必须联网激活方案均另行评审，不纳入本规划。

### 8.6 安全上线门禁

未认证的工具/文件/WS/SSE全部拒绝；read角色所有写工具拒绝；writer自批拒绝；撤销token立即失效；越scope路径/双链解析/搜索snippet/引用/事件不可泄漏；绝对路径、保留目录、符号链接越界拒绝；完整TLS与跨域/CSRF/Host校验；配额/大请求/连接限流；无stacktrace/密钥泄漏；断网重试去重与审计；备份恢复演练。

以上负例全部必过。内网不等于可信边界，不能以“先部署局域网”跳过认证。E应有独立安全复核者，不能由实现者只给出“看起来没问题”。

### 11.2 假设 Obsidian 明天上线同样的 Agent 插件生态

A的Timer/事件触发、C的摘要导入、D的frontmatter日期与E的HTTP接口都能被复制，不能自称护城河。Gemini Scribe已有定时与hooks，官方obsidian-skills也说明Agent能操作Obsidian；竞争前提必须按“接口并不稀缺”处理。

Kwey可积累的优势是**写入纪律×信任数据×低负担产品闭环**：统一服务入口、来源/当前版本审阅、可理解的提案、过期拒绝、跨入口一致性、故障解释与本地保存的用户决策历史。它们使“会写”变成“敢委托”，但不能约束绕过Kwey直接改文件的程序，因此不是不可复制的强技术垄断。

| 方向 | 对手复制功能后仍可能保留的优势 | 不应夸大的部分 |
|---|---|---|
| A | 固定职责质量、安静的队列、从试跑到批准的一致体验 | 定时/文件事件本身没有壁垒 |
| B | 多入口默认执行的写入来源与版本审阅；随用户使用积累的决定历史 | 没有防篡改、无法控制外部程序，迁出不是技术障碍 |
| C | 在Verbot/其他Agent之间的标准输入与可检索交接、来源纠错 | 摘要/导入格式易复制；不能靠专有格式锁用户 |
| D | 经用户长期标注的有效范围和替代链、对检索影响的实际评测 | 日期字段/降权规则易复制；模型“自动保鲜”未成立 |
| E | 自托管交付、权限治理与支持信誉、真实试点客户关系 | 协议和席位许可不是壁垒，安全维护是持续成本 |

验证护城河的可用问题：“同样的库和模型、同样能调用工具，用户是否更愿意在Kwey授权持续工作，且三个月后更少误改/更快审阅？”在获得这种数据前，只称战略假设。
